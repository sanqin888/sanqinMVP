## 架构、身份与业务所有权

- Phase 1 的基线和 Phase 2 的关闭是历史证据；后续开发继续遵守模块化单体、唯一事实所有者、稳定业务 ID 和内部数据库 ID 分离的规则。完整边界见 AGENTS 和当前依赖图，不为缩小计数添加透传公共 API 或隐藏依赖循环。
- Catalog 拥有当前菜单配置；Pricing/Offers 拥有计算、活动和规则；Benefits 拥有顾客持有的积分、余额、券及预占。管理页面只调用所属上下文能力，不拥有这些事实。订单成交快照不得用当前配置重新解释。
- Identity 拥有认证/验证挑战，Customer 拥有资料、地址、同意授权；Messaging 拥有投递、模板、回执和抑制策略，不决定业务上为什么发消息。旧阶段对 `MembershipService.getMemberSummary()` 的复合读模型、事件总线等记录只能作为当时的债务定位，当前是否仍存在以实现/依赖图为准，不能直接照旧清单新建反向公共依赖。
- Orders 拥有报价/订单快照、订单生命周期、变更、取消和履约意图；Payments 拥有支付事实，Print 拥有投递任务、模板、重试/确认与幂等。已完成的持久化生命周期/打印收缩不得退回内存事件作为跨进程唯一交付保证。支付、计价、退款中的事务一致性接缝不能仅为减少依赖计数而拆开。
- POS/Auth/Uber 的合法组合接缝和 owner-local persistence 不要求归零。Phase 7 的结论是 **SOURCE / ARCHITECTURE CLOSED**，没有宣称所有独立设备、供应商和门店运行场景均生产验收完成。打印协议及已部署代理版本仍按独立发布/兼容门禁处理。

- Loyalty 策略由 Benefits 的 `LoyaltyProgramPolicy` 及公共 policy reader/writer 拥有。原十项 earn/redeem/referral、tier multiplier/threshold 字段的 BusinessConfig/BrandConfig 镜像与传播已收缩；不得恢复旧读写或同步回退。完整字段清单与迁移证据在 [Loyalty 归档](../archive/architecture/benefits-loyalty-policy-contraction-plan.md)，历史 SQL 保留。
- `MenuCategory` 和 `MenuOptionGroupTemplate` 是非空 Store 所有权根，后代继承所属 Store；选项绑定、固定组件和目标商品不能跨 Store。`MenuPackagingType` 在该工作包中仍为品牌可复用字典。Catalog `stableId` 仍全局唯一，不改成复合 ID，也不重写订单、Uber 或打印的历史引用；旧 `/admin/menu/full` 已收缩。
- `OrderItem.optionsJson` 是成交时选项/计价快照，`componentsJson` 是成交时实际组件快照；二者都继续保留。当前 `MenuItemComponent` 与 `targetItemStableId` 只用于生成新快照，不能重建历史。已关闭的回填工具/读时兼容不再作为常规任务；历史软删除菜单行与迁移历史保留，不因归档而物理清除。

## Accounting 的权威与报告口径

- canonical Accounting Journal、Chart of Accounts 及受审源事实拥有财务权威；Admin/Web 不从 Orders 或 Expense 表自行重算财务金额。Posting、审计、幂等、期间锁和不可变历史规则继续适用，不能用 UI 总额或金额相近推断外部结算成功。
- Expense 分类回答“花在什么上”，`paidFromAccount` 回答“资金来自哪里”。历史 v1/NULL funding version 的 payment-allocation 含义冻结；v2 由 split-level 出资账户分组，可为一个 ExpenseDocument 生成多份平衡 Journal，分别使用幂等键。不得从平衡的混合借贷分录倒推出未记录的 split 归属，也不把账户写进分类名。
- `includeFundedExpensesInManagementReports` 只影响相应 Expense v2 分组在 Management P&L/费用分析中的包含范围；不隐藏 canonical Journal、真实账户变动、审计、资金流或税务事实。财务 Trial Balance 不得复用 Management 过滤器。
- Trial Balance 基于 JournalEntry → JournalLine → Account，按单一币种、**WHOLE_LEDGER** 读取，不做 FX 相加或 Store 筛选。历史停用账户只要有分录就保留；每条 line 单侧、每份 Journal 和期初/期间/期末借贷均须平衡，ASSET/EXPENSE 正常方向为借方，其余为贷方，contra 账户自然形成负正常余额。
- 日期按业务 IANA 时区处理 date-only 范围；早于 `accountingStartDate` 的 from 截断到起点，to 完全早于起点则拒绝。起点到报告前的分录参与期初，显式 `OPENING_BALANCE` 即使在 from 当日也归期初；不能凭空生成期初或从日期推断期间已关闭。零期初 Balance Movement 不宣称真实绝对 Balance Sheet；正式期初须另审并记入平衡的期初 Journal。原 2026-06-01 / Toronto / CAD 及生产数量是当时证据，不锁死未来配置。
- Funds 转账/归属纠正通过 Journal-native 增量事实，显式选择资金账户；不按数组第一项自动指定银行。归属纠正需要说明，不能就地改写 provider payout、Payroll 或银行证据，闭账期仍须遵守重开/调整治理。

## Admin 运营、销售与营销

- B5 / Admin Business Overview 是 Store 运营监控，Accounting 保持财务权威。经营时间历史的 `CURRENT_CONFIGURATION_ONLY` 不能当完整历史；Print 健康无公共 seam 时保持 `UNAVAILABLE`，不得猜测在线。
- Admin Sales Analytics 使用选中 Store 和 Store 时区，金额来自 Accounting；Management P&L 是 whole-business / whole-ledger，不能以 Store 选择器暗示单店口径。天气、法定节假日/长周末是 Reporting 的解释性上下文，与 Store 当前营业例外分开；天气失败不应抹掉 canonical Sales，也不把相关性称为因果。
- 经营/可售历史的后续捕获按 Backlog 和所属 owner 文档推进，捕获前未知历史不回填为零或从当前配置反推；已关闭 DATA-A–F 不自动重开 DATA-G。
- Marketing 使用数为 distinct `(activity, Order)`，折扣取接受的成交时 adjustment，受影响数量按实际目标行；历史原价证据不足时保持 `UNAVAILABLE`，不得套用 Accounting 专属历史覆盖规则。
- `associatedSalesCents` 为使用活动订单的促销/券/积分后商品小计，税、配送费和卡附加费前；它是关联指标，多活动金额不能相加当总营收，也不声称增量因果或 V1 退款净额。Today/7d/30d/90d 以选中 Store 的本地日为窗口，活动发生时间用 Orders sale occurrence，不能用浏览器时间或订单创建时间替代。后继 Daily Special 父活动/weekday 口径见 [MKT 归档](../archive/architecture/admin-marketing-overview.md)。
