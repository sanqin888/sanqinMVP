## 1. Purpose

Phase 9 owns the modularization and L3 integrity work for the `accounting-reporting-analytics` context. The intended owner scope is accounting ledger/expense operations, revenue posting, settlements/reconciliation, reporting/export read models and analytics ingestion/query. Orders, Payments, Brand/Store and External Channels remain the owners of their business facts and provider identities; Accounting may consume explicit facts/capabilities but must not acquire their persistence ownership.

This phase is not a file-layout rewrite. It must preserve current production behavior unless a later explicitly authorized slice changes accounting semantics. In particular, Slice 0 does **not** authorize changing revenue-recognition rules, removing open-period edit/delete behavior, changing persisted identity fields, creating Prisma migrations, altering Uber provider wire behavior or modifying production Web Clover behavior.

## 3. Hidden cross-owner persistence debt

### 3.1 Accounting -> Orders persistence

`AccountingService` directly queries Orders persistence for several behaviors:

- validating an ORDER-sourced accounting transaction against `Order.orderStableId`;
- `autoAccrueOrderRevenue()` reading order status, `totalCents`, `paidAt`, `channel` and `paymentMethod`;
- `dimensionSlice()` reading order totals grouped by channel/payment method.

The existing auto-accrual implementation posts `Order.totalCents` directly as accounting income. This is provisional behavior only. The Accounting Web sales page already states that order total cannot be treated as revenue directly because tax, discounts, delivery, surcharge, refunds and stored-value tender require explicit posting rules. Phase 9 must not re-label the current query as a canonical Revenue Posting capability merely by placing it behind an Orders public reader.

### 3.2 Reports -> Orders internals

`ReportsService` directly queries `Order` / `OrderItem` and deep-imports `readOrderItemComponentsSnapshot()` from Orders internals. Existing characterization is valuable and must be preserved: historical combo quantities are based on immutable `componentsJson`, and current menu configuration is not used to reconstruct historical sales composition.

### 3.3 Accounting -> Uber persistence

`AccountingAutomationScheduler` correctly calls the public `UBER_EATS_REPORTING` capability, but first directly queries `UberStoreMapping` for provider `uberStoreId` values. The current public reporting port also asks callers for `storeUuids`, leaking provider identity into Accounting. The target direction is for External Channels to resolve provider targets internally from SanQ business identity/reporting intent.

This contraction is deferred until a later Phase 9 slice because Phase 8 financial-report success replay is still `CODE READY / LIVE TEST BLOCKED BY UBER CAPABILITY`; Slice 1 must not reopen that provider seam.

## 4. Public-cycle constraint for Reporting

A naive `Reports -> Orders public API` contraction is unsafe because the current graph already has:

`Brand/Store -> Reporting`

for Homepage featured-item ranking, while Orders legitimately consumes Brand/Store public capabilities. Adding a lasting `Reporting -> Orders` public dependency can therefore form:

`Brand/Store -> Reporting -> Orders -> Brand/Store`

This phase must keep `legacyPublicCycleComponents=[]`. Before moving Reporting ownership, the implementation must choose a cycle-safe design such as a Reporting-owned outbound query port wired only at composition, or a purpose-built/versioned reporting projection where consistency and replay requirements justify persistence.

For canonical Revenue Posting, the preferred architecture is stronger than a synchronous query: Orders/Payments should publish/version the financial facts they own, and Accounting should idempotently consume/replay those facts into Accounting-owned state.

## 5. L3 financial-integrity findings

### 5.1 Transaction / audit atomicity gap

The base transaction mutation methods currently perform period checks, `AccountingTransaction` mutation and `AccountingAuditLog` creation as separate database operations. This leaves theoretical concurrency/failure windows where a transaction can be written after a concurrent period close or a transaction mutation can commit while its audit record fails.

Expense-document split creation already demonstrates the repository's accepted pattern by using `prisma.$transaction(...)`. A later Phase 9 L3 hardening slice should make financial fact mutation, close-state enforcement and required audit evidence atomic without changing the HTTP contract first.

### 5.2 Audit coverage is not complete

Manual/inbox expense flows create accounting transactions through `AccountingOperationsService` but do not currently create the same `AccountingAuditLog` evidence as the base transaction CRUD path. Phase 9 must define a single owner-internal invariant for traceable accounting writes instead of assuming the current audit table is complete.

### 5.3 Ledger mutability is a product/accounting decision

Current open-period transaction APIs support update and soft delete with optimistic concurrency. The long-term L3 target may instead require stricter append-only/reversal semantics, but that is a behavior change and is not authorized by Slice 0. Existing behavior must be characterized and preserved until a separate semantic decision is explicitly approved.

## 6. Persisted identity naming findings

The original Slice 0 audit found generic persisted names including `AccountingTransaction.orderId`, `createdByUserId`, `updatedByUserId`, `confirmedByUserId`, `closedByUserId` and `operatorUserId`. Slice 7-A has already removed the retired Order linkage/source contract. Slice 7-B now separates the remaining identity spaces explicitly: human-only fields use `*UserStableId`, while Journal/Audit fields that legitimately contain either a human user stable ID or an Accounting system actor key use `*ActorRef`. This avoids misrepresenting values such as `system:accounting-revenue-posting` as User identities while still keeping DB UUIDs out of the Accounting contract.

Slice 7-B is Class B persisted-contract work. The source/schema rename is authorized, but the migration must be user-generated and reviewed separately; existing Journal/Audit values must be preserved exactly rather than dropped/recreated.

### 15.1 Double-entry is now the target Accounting ledger model

The current `AccountingTransaction` model is an operational single-record income/expense/adjustment/transfer ledger and is no longer the intended terminal architecture for Phase 9. Before canonical Revenue Posting is implemented, Accounting must move to a minimal double-entry core so Revenue Posting, refunds, provider receivables, fees, taxes and settlements are defined once against balanced accounting entries rather than being rebuilt later.

The target design direction is a SanQ-sized Chart of Accounts plus balanced journal entries/lines, conceptually:

- account classifications capable of representing at least **ASSET / LIABILITY / EQUITY / REVENUE / EXPENSE**;
- one journal-entry header carrying stable business identity, source/fact identity, posting version, idempotency and audit/reversal references as required by the final design;
- two or more journal lines whose total debits equal total credits;
- existing operational categories such as food sales, delivery, ingredients, rent and utilities retained as reporting/operating dimensions where useful instead of being mechanically collapsed into the account hierarchy.

This decision does **not** authorize a full ERP redesign, a specific persisted schema, a particular Chart-of-Accounts numbering system, or a change from current open-period update/soft-delete semantics to append-only/reversal semantics. Those details require the Slice 5A audit and, for persisted changes, separate Prisma/migration authorization.

The low-risk migration window remains favorable: the Slice 0 production inventory found no `AccountingTransaction`, `AccountingAuditLog`, `AccountingPeriodClose`, `PlatformSettlementRecord` or `UberFinancialReport` rows. A later 2026-09-11 read-only inventory found the operating Orders dataset had continued to grow and also confirmed that historic Unified Payment Core tables do not provide a complete historical payment-fact source, so historical replay must not assume `PaymentTransaction` coverage.

### 15.2 Revenue recognition and platform settlement are separate facts

Canonical Revenue Posting answers what SanQ sold, what tax/delivery/surcharge components belong to the sale and what confirmed sale/refund/amendment facts changed that revenue. Platform settlement answers how a provider later settled its receivable after commission, marketing, subsidies, chargebacks, advertising, adjustments and payout timing. Settlement data must not overwrite the original order sale merely because the provider later deducted money.

For Uber Eats, the production-target order integration is treated as essentially terminal for the order-lifecycle side: a provider-confirmed cancellation before delivery is an order/cancellation fact that can reverse or prevent revenue posting. Post-delivery customer complaint deductions, chargebacks and other Uber-side financial actions belong to settlement/adjustment facts and must not mutate the original completed sale into a synthetic cancellation.

`PENDING_MANUAL`, `UBER_MANUAL_REFUND` and similar manual-refund states are transitional compatibility only. After Clover POS synchronization and authoritative provider-side refund/cancellation flows are live, new canonical financial posting must be driven by confirmed Payments/External-Channel facts rather than a permanent manual-refund branch. Historical confirmed manual records still require replay compatibility; pending/unconfirmed requests are not revenue reversals.

### 15.3 Historical Clover / Uber Eats / Fantuan financial coverage starts 2026-06-01

### 17.1 Current-state findings

### 17.2 Target intake ownership and persisted concepts

Slice 5C should introduce an Accounting-owned intake/evidence layer before any automatic journal posting. Recommended persisted concepts are:

- **SourceArtifact** — immutable acquisition evidence with stable artifact identity, acquisition mode (`EMAIL`, `MANUAL_UPLOAD`, `PROVIDER_API`), raw/content hash, MIME/input kind, transport metadata and stored evidence location/text;
- **ParseRun** — parser identity/version, parse status, normalized extraction result and error/retry evidence for replayable parsing;
- **InboxItem** — review/classification state, trust/quarantine decision and the relationship between one artifact and the downstream Accounting domain object;
- **TrustedSender** — UI-managed sender allow-list controlling automatic intake eligibility only; it does not assign provider identity, document type or accounting treatment;
- **ProviderFinancialDocument** — canonical provider financial header for Clover/Uber/Fantuan evidence, with provider, document scope/type, merchant/store identity, statement period, payout/settlement lifecycle timestamps, parser version, revision/supersession identity and preserved raw evidence;
- **ProviderFinancialLine** — extensible raw + normalized financial components with integer minor-unit amounts, tax role and posting treatment.

`ProviderFinancialDocument` is intentionally broader than a model named only `PlatformStatement`: Clover Daily Closeout is a financial control document but is not a processor statement. Provider-specific lifecycle dates such as `statementPeriod`, `settledAt` and `payoutAt` belong on these source facts rather than on generic `AccountingJournalEntry`.

### 17.3 Duplicate, revision and review semantics

5C should separate three identities instead of treating every replay as the same duplicate class:

1. **transport identity** — for example Gmail message + attachment/part identity or Uber report workflow/section identity;
2. **content identity** — SHA-256 of raw file bytes or deterministic normalized email-body content, independent of Gmail message ID;
3. **business identity** — provider + merchant/business scope + document type/scope + statement period/reference.

A byte-identical statement sent through a second email is a content duplicate. A corrected statement with the same business identity but different content is a **revision**, not a duplicate; it must supersede/link to the earlier evidence without silently overwriting already reviewed or later-posted facts. Unknown/untrusted material is preserved for quarantine/review rather than discarded. Formal Journal posting remains outside 5C and review-gated in later posting slices.

### 18.32 Accounting image OCR + post-confirm binary retention

Active image-recognition review found the old ordering backwards for evidence quality: the original image bytes were stored and hashed, but OCR first passed through the legacy 2400px / WebP quality-85 receipt compressor and then through the OCR-specific preprocessing pipeline. The authorized correction separates recognition from retention. OCR now consumes the original uploaded bytes and performs only the OCR-specific rotate / max-3000px / grayscale / normalize / sharpen / lossless-PNG preparation before Tesseract. OCR text normalization preserves line structure instead of flattening all whitespace. A real Tesseract/preprocessing failure now reaches the existing parse-failure path and records `AccountingParseStatus.ERROR`; a successful OCR execution that yields no readable text remains a successful parse with `NO_READABLE_TEXT` review metadata.

Long-term image compression moves strictly after confirmed Expense posting. `AccountingSourceArtifact.contentHash`, original byte size, MIME type and original filename remain the immutable identity of what the operator/Gmail actually supplied; `AccountingExpenseDocument.fileHash` therefore continues to mean original-source SHA-256 even after the original binary is later purged. Image Expense attachment references use the stable logical route `/accounting/inbox/artifacts/:artifactStableId/content` rather than a physical filename. Before retention acceptance that route serves the original; after acceptance/purge it serves the retained WebP without rewriting confirmed Expense or Transaction attachment URLs.

A new Accounting-owned `AccountingArtifactBinaryRetention` lifecycle separates source identity from current binary storage. Image acquisition creates `ORIGINAL_PRESENT`. Only an Inbox item already `CONFIRMED` as a confirmed `EXPENSE_DOCUMENT` may generate a compression candidate. Operators can repeatedly replace the unaccepted candidate using `SPACE_SAVER` (1800/q78), `BALANCED` (2400/q85), `HIGH_QUALITY` (3000/q90), or `NEAR_ORIGINAL` (4096/q95), previewing original versus candidate dimensions/size before accepting. Re-generating only replaces candidate evidence; it never touches the original. Choosing to keep the original discards the unaccepted candidate.

The Accounting Inbox now has a persistent **Image optimization** queue rather than relying only on the immediate post-confirm dialog. The queue is read from confirmed Expense Inbox items whose image retention state is `ORIGINAL_PRESENT`, `CANDIDATE_READY`, or `PURGE_PENDING`. `ORIGINAL_PRESENT` entries can generate a new default preview, `CANDIDATE_READY` reopens the exact already-generated derivative without silently recompressing it, and `PURGE_PENDING` exposes only the recoverable finalize path; it cannot be rolled back to “keep original” after deletion acceptance. Closing or refreshing the browser therefore never loses the operator entry point. `COMPRESSED_ONLY` leaves the queue automatically.

Acceptance is explicitly recoverable rather than pretending filesystem deletion is transactional. The writer first copies the verified candidate hash/size/MIME/dimensions/profile into retained fields and records `PURGE_PENDING` plus operator/time/policy-version audit evidence. The service then removes the original physical file; only after that succeeds (or an idempotent retry observes it already absent) does the writer record `COMPRESSED_ONLY` and `originalPurgedAt`. A crash before removal therefore leaves the original intact; a crash after removal but before finalization can safely resume from `PURGE_PENDING`. Candidate and original hashes are re-verified against their recorded identities before destructive acceptance. The retained WebP has its own hash and never replaces the original `SourceArtifact.contentHash`.

This changes the previously documented 5C-B promise that raw SourceArtifact binary must remain physically available forever, under explicit operator authorization. For evidence that reaches confirmation, the immutable **source identity and parse/audit evidence remain permanent**, while confirmed image binary retention becomes policy-controlled and destructible only after a human approves the exact derivative that will remain. “Purge” in this slice means removal from SanQ's active Accounting uploads storage; it does not claim deletion of an independent Gmail attachment, filesystem snapshot, or external backup copy. ### 18.33 Manual upload library + evidence-state permissions

Production verification of the PDF review path exposed a UI/retention mismatch: a byte-identical manual re-upload correctly entered `DUPLICATE`, but the Web UI still displayed the generic “added to Inbox” success message and the duplicate raw bytes were left as a second physical file. Permanent deletion does not keep a tombstone/audit row because the user explicitly chose complete removal for never-confirmed manual uploads.

The state permissions are authoritative at the API/writer boundary, not only in the Web UI:

| Inbox state / ownership | Continue/review | Abandon | Delete permanently | Notes |
| --- | --- | --- | --- | --- |
| `MANUAL_UPLOAD + PENDING_REVIEW` | Yes | Yes | Yes, unless protected by another evidence chain | Ordinary unconfirmed upload. |
| `MANUAL_UPLOAD + QUARANTINED` | Yes after trust resolution | Yes | Yes, unless protected | Included for completeness even though manual intake normally uses `NOT_APPLICABLE` trust. |
| `MANUAL_UPLOAD + ERROR` | No normal parser continuation until retried/fixed | Yes | Yes, unless protected | Error evidence can be abandoned instead of remaining stuck. |

### 18.35 Accounting Inbox receipt-image OCR quality hardening

Production read-only evidence from the first real long grocery receipt showed that the §18.32 source-ownership fix was working but recognition quality was not: the original JPEG bytes were hashed/stored and passed directly into `extractAccountingImageText()`, Tesseract exited successfully, yet the generic parse stored only about 229 characters of mostly nonsensical OCR and therefore produced no date, tax or total. The defect is consequently inside the OCR preparation/segmentation/quality boundary rather than the image-retention lifecycle or the downstream Accounting parser. The former OCR pipeline constrained both width and height to 3000px with `withoutEnlargement`, so a tall receipt could be height-limited until its already-narrow text became even smaller; it also kept a dark surrounding background, used only one grayscale/normalize/sharpen candidate, always invoked `eng+chi_sim`, and forced `--psm 6` even when the image contained a long retail receipt plus a second terminal-receipt block. Finally, Tesseract exit code `0` alone was treated as parse success, so non-empty garbage remained `SUCCESS` evidence.

The hardened pipeline stays on the original acquired bytes and the existing local Sharp/Tesseract stack, and is intentionally not sized around the Foody Mart sample. Sharp first applies EXIF orientation. A bounded low-resolution analysis preview estimates the effective receipt/content width so a narrow paper strip surrounded by large dark margins does not inherit the full photograph width for scaling decisions; the preview is never used as OCR evidence. Short receipts may stay as one OCR region, while taller receipts are split adaptively into ordered vertical regions with small overlaps according to aspect ratio and estimated receipt width. Each region is independently trimmed when using a receipt-focused strategy, resized toward a 1800px working width without exceeding the per-region resource guard, converted to grayscale, normalized, sharpened and encoded as lossless PNG. This prevents a receipt that is several times longer from being globally squeezed into one fixed-height image and progressively shrinking its text. Overlap output is reassembled in source order with deterministic boundary-line deduplication so parser-visible line structure remains intact.

The primary strategy keeps the enhanced grayscale regions; only when its deterministic receipt-quality score is not strong enough does OCR run a second strategy with binary thresholding for faint thermal-paper text. Both receipt strategies use English-only Tesseract with `--psm 4`, 300-DPI interpretation and engine-level inter-word-space preservation. A third untrimmed contrast strategy retains `eng+chi_sim / --psm 6` only as a bounded fallback when the receipt passes remain weak. A strong primary strategy therefore avoids binary/mixed-language fallback, although a genuinely long receipt may still require multiple Tesseract region processes within that one strategy. There is no fixed 50/50 receipt/terminal split or vendor-specific length assumption: segmentation is geometry-driven and applies equally to grocery, restaurant, fuel, hardware and other long-form receipts. Sharp also does not provide a safe automatic perspective-correction/deskew primitive for this use case; no new dependency is justified by current evidence, so arbitrary-angle deskew/perspective correction remains deferred unless production verification proves it is a blocker.

Multi-pass winner selection is deterministic and receipt-oriented rather than length-oriented. Each normalized candidate retains line breaks and is scored from printable-character ratio, normal ASCII alphanumeric-token ratio, money/date matches, receipt signals (`SUBTOTAL`, `TOTAL`, `HST/GST/TAX`, `DEBIT`, card brands, `APPROVED`, `PURCHASE`, etc.), and line-level structure, with penalties for symbol/CJK-heavy noise lines and excessive one-character alphanumeric tokens. Ties resolve by the same fixed candidate order. A strong English receipt result avoids the mixed-language third pass; weak results may use it. Successful empty output preserves the existing `SUCCESS + NO_READABLE_TEXT` review semantics, but non-empty text that fails the deterministic minimum quality/evidence gate now throws through the existing acquisition failure path and records `AccountingParseStatus.ERROR` instead of `SUCCESS + garbage`.

Resource bounds remain explicit: source image upload stays capped by the existing 20MB / 80M-input-pixel policy. Geometry analysis is bounded to a 1000px preview and is used only to estimate receipt width/segment count. OCR regions target 1800px working width and are individually capped at 5000px height, 9M pixels and 24MB; one strategy may contain at most 10 ordered regions and 64MB of prepared region buffers, with 180px working-space overlap. If preserving the configured text scale would require more than 10 regions, preprocessing fails closed instead of silently compressing the entire receipt. At most three preprocessing strategies are available and they execute progressively by OCR quality. Every Tesseract region process retains the 20-second timeout; combined OCR output for a strategy remains capped at 512KB. No retained derivative is used as OCR input. The post-confirm `ORIGINAL_PRESENT -> CANDIDATE_READY -> PURGE_PENDING -> COMPRESSED_ONLY` lifecycle, original source hash/identity, stable attachment URL and Upload-library permissions are unchanged. No Prisma schema/migration, npm/system dependency, public API, context direction, scanner allowance, PDF/CSV/provider recognition rule, Journal authority or financial posting policy changes are part of this hardening.

Focused regression coverage uses synthetic/de-identified receipt images and text only: original-byte ownership and OCR-error persistence remain pinned by the acquisition tests; new OCR tests cover dark-background trimming, a high-aspect-ratio synthetic very-long receipt that must become multiple bounded OCR regions rather than one globally shrunken image, explicit fail-closed behavior beyond the region budget, ordered overlap merge/deduplication, clear-receipt non-lossy preparation, deterministic winner selection, English-first/mixed fallback behavior, line preservation, garbage rejection and empty-text semantics. Receipt-quality fixtures use generic merchant/item names rather than copying Foody Mart as a recognition template. Existing image-retention writer/query/architecture tests remain the regression guard that OCR changes do not enter the retention lifecycle.
